# Weather Pro 决策体验 MVP 设计

## 目标

把 Weather Pro 从“展示天气并附带通用提示”升级为真正可行动的出门决策助手。用户应能针对通勤、户外和家庭场景获得不同建议，在本机设置可用的雨前提醒，并在移动端首屏看到最重要的结论。

本规格优先于管理后台实施。管理后台使用独立规格，避免统计系统阻塞用户价值交付。

## 用户范围与成功标准

目标用户是不希望分析大量天气数字、只想快速决定如何出门的普通用户。

成功标准：

- 三种场景返回不同的行动建议，而非只更换标题。
- 每条建议说明“结论、原因、行动”，且能从当前天气数据推导。
- 用户能在本机完成雨前提醒的开启、配置、触发和关闭闭环。
- 浏览器关闭后无法保证提醒这一限制必须在授权前明确展示。
- 移动端首屏无需滚动即可看到地点、核心建议、当前温度、降雨状态和评分。
- 用户能使用当前位置并在本机保存最多五个常用地点。
- 评分展示组成因素、更新时间和数据来源。
- 会员付费不再作为未实现的主行动入口。

## 范围拆分

### 场景建议引擎

在 `shared/advice-engine.js` 新增前后端共用的纯函数建议引擎，输入标准化天气数据，输出统一结构：

```js
{
  mode: "commute",
  headline: "10:55 起有中雨，建议提前出发并带伞",
  summary: "未来两小时降雨并伴随较强东风",
  decisions: [
    { key: "departure", status: "warn", label: "出发时间", value: "建议 10:35 前出发", reason: "10:55 起降雨" }
  ]
}
```

三种模式使用不同规则：

- `commute`：优先处理首场降雨时间、当前降雨、风速、预警和通勤出发时间。
- `outdoor`：优先处理连续无雨窗口、风速、UV、体感温度和雷电风险；输出跑步或骑行是否适合。
- `family`：优先处理体感温度、UV、天气预警及穿衣、感冒等生活指数；输出儿童和老人相关建议。

建议引擎不得声称当前数据无法支持的医学结论。数据缺失时输出“数据暂不可用”和替代判断依据，不猜测。

### 评分解释

现有评分逻辑扩展为：

```js
{
  value: 64,
  label: "需准备",
  base: 92,
  factors: [
    { key: "rain", label: "中雨", impact: -22 },
    { key: "wind", label: "风速较高", impact: -10 }
  ]
}
```

服务端同时返回：

- `updatedAt`：本次天气结果生成时间。
- `source`：`Mock` 或 `QWeather`。
- `isPartial`：是否存在部分上游数据失败。

前端在评分卡中提供可展开解释，展示基础分、扣分项、更新时间和来源。

### 本机雨前提醒

提醒配置保存在 `localStorage`，结构版本化：

```js
{
  version: 1,
  enabled: true,
  location: { id: "101010100", name: "北京", lon: "116.40529", lat: "39.90499" },
  leadMinutes: 20,
  activeStart: "07:00",
  activeEnd: "22:00",
  lastNotificationKey: "101010100:2026-06-25T10:55+08:00"
}
```

交互流程：

1. 用户点击“雨前提醒”。
2. 页面先解释本机提醒的能力和限制。
3. 用户选择地点、提前量和生效时段。
4. 用户主动点击“允许通知”后才请求浏览器权限。
5. 保存配置并立即执行一次检查。
6. 页面打开期间每五分钟检查一次分钟降雨；页面重新可见时立即补查。
7. 首场降雨进入提前量范围且当前处于生效时段时发送通知。
8. 以地点和降雨时间组成去重键，同一场降雨只通知一次。

权限被拒绝或浏览器不支持通知时，保留配置但明确显示“仅页面内提示”，提供重新检查权限的说明。提醒请求失败不得影响天气查询。

### 当前定位与常用地点

- 只有用户点击“使用当前位置”后才调用 Geolocation API。
- 定位成功后，将经纬度传给地点查询接口，选择最近的城市或区县。
- 定位拒绝、超时或不可用时显示可恢复错误，并保留手动搜索。
- 常用地点保存在版本化 `localStorage`，最多五个，可添加、切换和删除。
- 不把精确位置发送到匿名统计后台；天气查询所需经纬度只用于当前 API 请求。

Mock 模式下，当前位置使用与坐标最接近的内置 Mock 城市，保证开源用户能测试完整流程。

### 移动端首屏

宽度不超过 640px 时按以下顺序展示：

1. 品牌、提醒入口和地点控制。
2. 紧凑的场景建议标题与一行原因。
3. 当前温度、天气、两小时降雨和评分组成的摘要卡。
4. 通勤、户外、家庭切换。
5. 分钟降雨、预报、场景详情和其他内容。

移动端主标题最多两行，说明文案最多两行。桌面布局保留现有视觉语言和动态天气效果。所有交互目标至少 44×44 CSS 像素，不产生横向滚动。

### 会员付费

本阶段不实现支付。现有会员卡从主流程移除，或改成不带价格和不可用购买按钮的“计划能力”说明。页面不得展示无法完成的“开通”操作。

## 共享模块边界

- `shared/advice-engine.js`：三种场景建议、可解释评分和数据元信息的唯一规则源。
- 服务端在核心天气返回时调用共享引擎生成可立即展示的初始建议。
- 前端收到详情数据并与核心数据合并后，再调用同一共享引擎生成包含分钟降雨和生活指数的最终建议。

该结构保留现有渐进加载速度，同时避免服务端和前端维护两套判断规则。

## 前端模块边界

- `src/reminder-store.js`：提醒配置读取、校验、迁移和持久化。
- `src/reminder-engine.js`：提醒时段判断、触发条件和去重。
- `src/favorite-locations.js`：常用地点存储与上限规则。
- `src/components/`：拆分地点选择、提醒设置、评分解释、移动摘要和场景面板。

现有 `src/main.jsx` 只负责页面编排和数据加载，不继续承载所有业务规则。

## 服务端模块边界

- `server/weather-service.js`：继续负责数据聚合，并调用建议引擎生成 `insight`。
- `server/app.js`：地点查询支持经纬度输入；不保存用户位置。

## 错误处理

- 核心天气失败：保留现有错误卡，并增加显式重试。
- 详情数据失败：继续展示核心天气，场景建议标注依据不完整。
- 定位失败：展示原因和手动搜索入口。
- 通知权限拒绝：不重复弹出系统授权，允许用户查看浏览器设置说明。
- 本地数据损坏：丢弃损坏记录并恢复安全默认值，不阻塞页面。

## 可访问性

- 搜索框提供可访问名称，不依赖 placeholder。
- 场景切换使用 `aria-pressed` 表达当前状态。
- 所有按钮和输入提供明显的 `:focus-visible` 样式。
- 动态建议通过克制的 live region 通知，避免每次天气细节加载都重复播报。
- 保留现有 `prefers-reduced-motion` 行为。

## 测试

- 建议引擎覆盖晴天、中雨、大风、高 UV、预警、缺失详情和三种场景差异。
- 评分测试覆盖每个扣分因素、上下限和解释总和。
- 提醒测试覆盖生效时段、提前量、去重、权限拒绝和配置迁移。
- 常用地点测试覆盖添加、切换、删除、重复地点和五个上限。
- API 测试覆盖经纬度地点查询和部分数据失败。
- 浏览器验证覆盖桌面、390px 移动端、键盘焦点、场景切换和提醒设置流程。

## 非目标

- 浏览器关闭后的后台 Web Push。
- 用户账号和跨设备同步。
- 原生应用、微信小程序和支付系统。
- 医疗建议或灾害预警替代服务。
