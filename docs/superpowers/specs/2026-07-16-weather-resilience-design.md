# 天气数据容错与友好降级设计

## 目标

当服务器到和风天气的网络链路短暂超时或部分接口失败时，页面仍提供可理解、可操作的天气状态，绝不展示 `0°`、裸 `°`、`湿度 %` 或 `能见度 km`。

## 已确认方案

采用完整容错方案：

1. 对可恢复的上游网络错误进行最多两次短重试。
2. 实时天气请求失败时，允许使用最近 30 分钟内的成功缓存。
3. 使用过期缓存时明确标记数据延迟，不能伪装成最新数据。
4. 预警数据不使用过期缓存，避免把已经失效的安全信息继续展示。
5. 没有实时数据和可用缓存时，前端显示明确的不可用状态和重试入口，同时保留仍然可用的预报内容。

## 服务端数据流

### 重试

- `QWeatherClient` 只对 `UPSTREAM_TIMEOUT` 和 `UPSTREAM_NETWORK_ERROR` 重试。
- 首次请求失败后最多重试两次，共最多三次请求。
- 使用短退避，避免瞬时连接抖动直接暴露给用户，也避免长时间阻塞页面。
- HTTP 错误、无效响应和鉴权错误不重试。

### 过期缓存兜底

- 每个缓存条目继续保留原有 `cachedAt`。
- 实时天气 `/v7/weather/now` 的正常 TTL 保持 8 分钟；网络重试仍失败时，可返回不超过 30 分钟的最近成功数据。
- 逐日和逐小时预报继续使用现有缓存策略，本次不扩大过期缓存范围。
- 预警接口禁止使用过期缓存。
- 使用过期数据时返回可机读元数据，使服务端建议和前端文案都能标记数据延迟。

## API 行为

- 实时天气成功：保持现有响应结构。
- 实时天气使用过期缓存：保留天气字段，并增加数据延迟标记。
- 实时天气完全不可用但其他核心数据成功：保持部分成功响应，但 `now` 为 `null`，错误数组包含 `now`。
- 所有核心来源失败：继续返回 502。

## 前端体验

### 有实时数据

- 正常显示体感、温度、天气、湿度和能见度。
- 使用过期缓存时，在数据来源区域显示“实时数据更新延迟，正在使用最近数据”。

### 没有实时数据

- 天气卡显示“实时天气暂不可用”。
- 温度、体感、湿度和能见度不渲染数字单位。
- 显示“重新加载”按钮。
- 若逐日、逐小时或预警数据仍可用，页面其他区域继续展示。
- 评分与建议明确为部分数据结果，不能把缺失值转换成 `0`。

## 测试

### 服务端

- 网络错误后重试并在后续尝试成功。
- 超时后重试次数不超过两次。
- 无效响应和 HTTP 错误不重试。
- 实时天气网络失败时返回 30 分钟内的过期缓存并标记延迟。
- 超过 30 分钟的缓存不再返回。
- 预警失败时不返回过期缓存。

### 前端

- `now` 缺失时不会生成裸单位或 `0°`。
- `now` 缺失时显示明确不可用状态和重试按钮。
- 延迟数据状态显示提示，完整数据不显示提示。
- 部分核心数据仍能渲染预报区域。

## 非目标

- 不引入新的外部缓存服务。
- 不更换天气供应商。
- 不将过期预警作为兜底。
- 不在本次修改中重构整个天气聚合协议。
